# FONTS5 Build and Guest Qualification

## Result

**Outcome B — partial qualification.** The authentic guideXOS UEFI source build, managed artifact audit, hosted font regressions, and authorized QAC/QEMU guest boot passed. Guest input opened Start Menu and All Programs, the taskbar context menu, and application windows; Task Manager could be moved and closed. TrueType selection remains unavailable through the production UEFI UI, and several requested dialogs and notification paths were not exercised. The bitmap UI shows wide glyph spacing and layout clipping, including the taskbar date.

The starting revision was `2c29f32df19e0f576f665e2a448a5f8e5f798cf6` on `FONT_SUPPORT`. Build outputs and screenshots were kept in the detached build worktree `D:\dev\guideXOSUEFI_FONT_SUPPORT_FONTS5_BUILD`; the source changes and this report are in the primary checkout.

## Provenance and build recovery

The initial checkout lacked generated build state; it did not require edits to `BUILD_INFRA`, `APP_MODEL`, `MODERN_INPUT`, or `main`. `BUILD_INFRA` was inspected read-only and did not supply these inputs.

- `out\rt` is an ignored runtime source checkout pinned by `Tools\Phase20\runtime-source.lock.json` to dotnet/runtime commit `9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3`. The checkout was clean after the build. The Phase20 source baseline and Phase22/23 inputs were reconstructed through their repository scripts. The lock records the Windows x64 NativeAOT toolchain and explicitly records that no runtime source adaptation was made.
- Phase29 proof metadata is produced by `Tools\Phase29\build_phase29_managed_notification.ps1` and staged by `Tools\Phase29\stage_phase29_image.ps1`. The top-level build invokes these and the Phase27–35 managed proof build/stage handoffs before generating the kernel admission identities.
- `guideXOS\obj\ManagedArtifactIdentities.g.cs` is generated by `Tools\ManagedArtifacts\managed_artifacts.py --stage generated` from the manifest-defined managed ramdisk payload sources. The same tool audits the built kernel, descriptors, staging files, and final RAM disk.
- `build.ps1` now provisions absent or stale pinned runtime inputs, runs the prerequisite proof handoffs, generates identities before kernel compilation, and performs the post-build RAM-disk audit. The source build used no temporary compile-only replacement files.

The clean build exposed and repaired several pipeline defects on `FONT_SUPPORT`:

1. The generated native stub object was omitted on a fresh build because the project evaluated an `Exists` condition before that object was generated. `guideXOS.csproj` now includes the generated `native_stubs.obj` unconditionally; the clean rebuild verified the object was present in the linker response and all 44 unresolved native symbols were resolved.
2. Phase26's proof build needed CRLF-safe source guards and a more robust RIP-relative LEA patch against the generated PE/map pair.
3. Phase31–35 stage scripts pointed at a nonexistent `obj\x64\Release` directory; they now use the actual `obj\Release` output. Phase35 verification now checks its persistent-read helper and syscall trampoline rather than reusing an unrelated Phase27 expectation.
4. The UEFI source build's TrueType code called `char.IsHighSurrogate`/`IsLowSurrogate`, which are unavailable in this target profile. The shared internal range classifiers in `TrueTypeFont` are now used by both text layout and shell rendering, with two UTF-16 boundary regression checks.
5. The project's legacy GRUB ISO target fails without `Tools\grub2\boot\grub\i386-pc\eltorito.img`. The production `build.ps1` assembles the UEFI ESP itself, so it now passes `-p:SkipISO=true` and does not invoke that unrelated ISO path.

## QAC and guest observations

Before the first launch, QAC reported Coordinator Online with zero QEMU processes and zero managed sessions. Reservation `d79ab154e9664f67b2857fadcc91ec42` was granted to project `guideXOSUEFI-FONTS5` in acceptance mode with QEMU PID 16824; it was released after that managed child exited. On resume, QAC again reported zero QEMU processes and zero managed sessions, so a second acceptance reservation was granted: `c36fbb3d629c425eb15e311f8b349ffa`, QEMU PID 25220. The second QEMU process was stopped through its QMP `quit` command. QAC reported the reservation **Released**, reason `Managed child exited.`, and final status Coordinator Online, zero QEMU processes, and zero managed sessions.

The guest ran QEMU 11.0.0 on `pc-q35-8.2`, with 1024 MiB RAM, two vCPUs, EDK2 x64 firmware, and the ESP directory attached as a FAT-backed disk. Serial evidence includes `DESKTOP_REAL_TEXT_RENDERED=1`, `TASKBAR_REAL_TEXT_RENDERED=1`, loaded desktop icon assets with zero fallbacks, and a continuous desktop heartbeat. At frame 3600 the sampled allocator reported 18,767,872 bytes, 26,638 successful frees, zero invalid/corrupt frees, and an unlocked thread pool.

The resumed session's latest serial heartbeat sample was frame 34,200: 30,396,416 allocator bytes, 93,662 successful frees, zero invalid/corrupt frees, and an unlocked thread pool. Input counters showed zero dropped keyboard or mouse events across 18 key IRQs and 228 mouse IRQs.

The bitmap default rendered the wallpaper wordmark, desktop labels, taskbar clock, and date. The 1280×800 guest screenshot shows the date clipped to `11/5/2` at the right edge; the existing bitmap clock compatibility test preserves the earlier placement that causes this, so it is recorded as a pre-existing bitmap-layout limitation rather than a TrueType regression. The date string was clipped in both guest runs.

Guest Start Menu and All Programs opened during the resumed run. All Programs showed the app list; narrow right-column entries truncated to forms such as `Compu...`, `Disk...`, and `Recen...`. The `All Programs` and `Shutdown` bottom buttons wrapped their last character to a second line. The shell uses visibly wide letter spacing on the bitmap text surfaces. The Firewall app opened from the list; its title, mode buttons, and body rendered, but the footer help text was clipped at the window edge. The Taskbar context menu opened on right-click and displayed `Task Manager`; selecting it launched the Task Manager window. Its title, tabs, columns, and rows were readable, and a horizontal title-bar drag moved the window before its close button dismissed it. The popup's lower edge overlapped the taskbar by several pixels. A later repeated Start-button click after the Task Manager interaction did not reopen Start Menu, so that repeat activation/focus path is recorded as inconsistent; the earlier Start Menu and All Programs screenshots prove the menu itself did open.

Full source search confirms `Taskbar.HandleUefiInput()` is called from the UEFI frame path in `guideXOS\Program.cs`; the earlier report that it was unreferenced was incorrect. That handler was exercised through the taskbar context menu. The TrueType selector remains internal and has no production UI caller, so only hosted selection/fallback behavior is qualified. Notifications, MessageBox, Shutdown, Save Changes, and repeated dialog/redraw behavior were not exercised in this guest run.

## Remaining work and hardware procedure

1. Add and review a production path that explicitly calls the existing validated TrueType selector, then repeat guest typography checks with bitmap and TrueType providers. Keep bitmap as the default and retain the hosted fallback coverage.
2. Investigate the inconsistent repeated Start-button activation/focus path and the visual clipping in All Programs, its bottom buttons, the taskbar context popup, Firewall footer, and taskbar date. Preserve the existing pixel-compatibility baseline unless layout changes are approved.
3. Exercise notifications, MessageBox, Shutdown, and Save Changes dialogs once a stable guest path is available. On **SARAH_DT** and the **ASUS VivoBook**, boot the same ESP from FAT32 USB using the firmware's one-time boot menu. Photograph the boot/desktop and collect serial output. Test the same bitmap and TrueType surfaces after the opt-in path exists. Use a known-good external USB mouse and keyboard, click inside the guest display to establish focus, and verify that each input reaches the guest before judging a UI control. If input still fails, record that as a platform input limitation and use the screenshot/serial evidence separately from typography acceptance. Hardware testing is recommended follow-up, not a gate for this hosted/QAC result.
