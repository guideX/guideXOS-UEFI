## Existing Phase 9 OpenDocument contract

The live implementation is `ApplicationServiceId.Shell` (`7`) and exposes `Begin`, `Observe`, and `Cancel`. The existing service accepts `ApplicationShellOpenRequest`; its `Document` target kind enters `CSharpApplicationShellService.Dispatch` and calls `OpenDocument`. Phase 32 reuses the same Ring 3 service transport and request envelope. The internal operation numbers are `1` for stable application-ID launch and `2` for OpenDocument.

The document value is the existing bounded filesystem-path string. It is not a URI, MIME identifier, or user-selected application. Both `ApplicationShellOpenRequest.MaxTargetLength` and `LaunchRequest.MaxTextLength` are 1,024 UTF-16 code units. The ABI copies the value as UTF-16LE. Its wire record has 2,084 bytes (including fixed 2,048-byte target storage); its typed response is 16 bytes.

The service validates a nonempty, bounded document string. Association resolution extracts the suffix beginning at the final period. `NormalizeExtension` prepends a period when absent and lowercases ASCII `A`–`Z`. It does not canonicalize or authorize a filesystem path. The association adapter passes the original bounded document string into the `LaunchRequest`; the selected target’s existing open implementation determines whether the resource can be read. Thus an associated but nonexistent `.txt` path reaches Notepad and returns `ResourceUnavailable` from its factory/open path. An empty target is `InvalidRequest`; an unassociated extension is `UnsupportedTarget`. The contract does not require a new document-address format or managed filesystem access.

For an associated document, `ModernFileAssociationAdapter` creates a `LaunchRequest.ForFile` with the association’s stable handler application ID, original document string, `open` verb, no caller-supplied source object, non-GXM file kind, and `LaunchActivationIntent.Launch`. `CSharpApplicationShellService` routes that typed request through the descriptor resolver and `ApplicationFactoryRegistry`. For `.txt`, the default association is `gxos.builtin.notepad`, and the factory is `NotepadApplicationFactory`. The successful target receives `LaunchRequestTargetKind.FileOpen` and the document value. Missing resources return a typed error without retaining a target. Neither alias routing nor a compatibility fallback participates in this proof.

## Managed SDK and authority boundary

The public SDK adds:

```csharp
GuideXosShell.TryOpenDocument(string document,
    out GuideXosLaunchResult launchResult)
```

`GuideXosShell.MaxDocumentLength` exposes the existing 1,024-code-unit contract bound. The API returns transport status as `GuideXosResult` and the Shell outcome as the existing typed `GuideXosLaunchResult` / `GuideXosLaunchResultCode`. Raw request/response records, service IDs, operation IDs, pointers, and transport methods remain internal. The public caller receives no process handle, App Model instance handle, factory identity, service context, or raw kernel object.

The SDK rejects null, empty, and over-bound input with `GuideXosStatus.InvalidArgument` and does not truncate. It encodes each managed `char` into the fixed UTF-16LE storage before making the synchronous `guidexos_pal_service_request` call. It retains no managed string pointer. The kernel copies the complete request, independently validates operation, record size, nonzero target length, 1,024-code-unit limit, response capacity, and reserved fields, validates the response buffer as writable user memory, decodes a kernel-owned string, and copies back only the fixed typed result.

The request carries no authoritative caller AppId, process handle, ApplicationInstance handle, Shell context, factory ID/pointer, association-selected target AppId, or launch authority. The kernel starts from the current scheduled Ring 3 process, reads its kernel-owned owner-instance value, validates that live `ApplicationInstance` through the registry, derives a fresh `ApplicationServiceContext`, checks that it resolves to the same owner and Shell service, and requires the requester lifecycle to be `Running` or `Activated`. The App Model then owns association choice, stable target, descriptor resolution, factory selection, LaunchRequest construction, and lifecycle.
